# Dreame X40 Pro Ultra — 최소 호환 패치

이 브랜치는 [dwyschka/Dreame-local](https://github.com/dwyschka/Dreame-local)의 **0.9.1 / `df9160cee933626f08c112d9159f9a66cea38ccc`**에 필요한 수정만 적용합니다. 기존 별도 백엔드를 다시 넣지 않습니다. 이전 0.7.1 실기 결과를 0.9.1 검증 결과로 간주하지 않습니다.

- 대상 모델: **X40 Pro Ultra / `dreame.vacuum.r2401`**.
- 개발 브랜치: `x40-pro-ultra/compat`. 포크의 `main`은 upstream 그대로이며 이 패치가 없습니다.
- 기존 두 자체 제작 저장소는 아카이브했습니다. 코드를 삭제하거나 운영 애드온을 정지한 것은 아닙니다.
- 원본의 라이선스 표기를 변경하거나 별도 재배포 권한을 부여하지 않습니다. GitHub 포크 외의 바이너리/릴리스 배포는 하지 않습니다.

## 범위와 현재 검증 상태

### 속성 조회 결과를 HACS에 전달

로봇의 `/recv/` 속성 조회 응답은 서버 캐시를 갱신하지만, 원본 HACS는 `/status/`를 구독합니다. 원본은 이 응답을 status 이벤트로 전달하지 않습니다. 따라서 서버의 상태와 HACS 상태가 달라질 수 있는 경로가 있습니다.

최소 수정은 `device.py`의 기존 `_handle_recv`에서만 합니다.

- 실제 장치 응답 중 `code=0`이고 값이 있는 속성을 기존 `properties_changed` 형식으로 전달합니다.
- 서버 캐시와 같은 값이어도 전달합니다. 서버 캐시는 최신이지만 HACS가 오래된 경우를 포함합니다.
- 음수/실패 코드 또는 성공 여부가 없는 응답으로 캐시를 덮어쓰지 않습니다.
- 이 전달 자체는 추가 로봇 RPC나 청소/복귀 명령을 발생시키지 않습니다.
- 지도 service 6은 별도 프레임 변환 경로가 필요하므로 이 일반 속성 알림에 넣지 않습니다.
- 기존 명령 ACK 결과와 pending-future 상관관계는 유지합니다.

**회귀 시험:** 원본 함수로 전달 누락과 실패 응답의 캐시 오염을 재현한 뒤, 수정본에서 `tests/test_state_sync.py`의 시험이 통과했습니다. 합성 응답에 대한 검사이며 실제 로봇의 복귀 전환을 다시 시험했다는 뜻이 아닙니다.

**운영 검증:** 업데이트 전 직접 로봇 조회와 서버 상태는 충전 완료인데 HA 상태는 복귀 중인 불일치를 다시 확인했습니다. 사용자 승인 후 기존 애드온을 `0.9.1-x40.2`로 업데이트·재시작하자 HA Core 재시작 없이 HA 상태도 `charging_completed`, vacuum도 `docked`로 수렴했습니다. 이후 읽기 전용 장치 조회에서도 충전 완료와 오류 0을 확인했습니다. 기존 stale 증상 해소는 관측했지만 새 청소/복귀 전환을 시험하지 않았으므로 해당 상황의 장기 재발 방지를 확정하지 않습니다.

- native HAOS amd64 이미지에서 같은 회귀시험 **8개 통과**, 앱 소스 hash **8개 일치**를 확인했습니다.
- Mac→HA 내부망 HTTP 업로드 canary는 200 응답뿐 아니라 파일 내용 readback까지 확인하고 시험 파일을 제거했습니다. 실제 로봇이 새 HTTP URL로 올리는지와는 별도 검사입니다.
- 현재 지도 PNG는 실제 파일 생성과 전체 decode를 확인했습니다. 로봇 이동 없이 실시간 위치·궤적 갱신을 증명한 것은 아닙니다.
- 기존 options·포트·boot·watchdog·데이터 mount를 보존하고 HTTP 업로드 포트만 추가했습니다. HA Core·공유기는 재시작하지 않았고 새 물리 명령을 보내지 않았습니다.

### 지도와 그 밖의 한계

**웹페이지 바로가기 (`0.9.1-x40.3`):** 관리자용 HA 사이드바 `드리미 X40`에서 기존 `/rooms` 페이지를 Ingress로 엽니다. 8099를 호스트에 새로 공개하지 않습니다. 실제 저장지도가 JSON `mapstr` 포장으로만 남은 환경에서 API는 지도를 읽지만 WebUI는 이를 거부해 지도 PNG가 404가 되는 문제를 재현했습니다. 기존 웹 decoder에 포장 해제만 추가했고, 유효한 raw frame·URL-safe 입력·손상 입력 처리도 회귀시험했습니다. 운영 적용 후 페이지·방 목록·PNG가 모두 200, 방 6개, PNG 972×760 전체 decode를 확인했습니다. 기존 상태 시험을 포함한 14개 시험이 native HAOS 이미지에서 통과했습니다. HA Core는 재시작하지 않았고 로봇 동작 명령도 보내지 않았습니다. 브라우저의 HA 로그인은 완료하지 못했으므로 인증된 iframe의 시각 렌더링까지 검증했다고 주장하지 않습니다.

- 원본의 저장 지도/PNG 표시는 확인됐지만 실시간 위치·궤적은 미검증입니다.
- 지도 프레임 수신/선택 경로를 별도로 조사합니다. 좌표·궤적을 임의로 만들지 않습니다.
- 청소/순찰 이력은 원본에서 미구현이며 이번 최소 수정 범위 밖입니다.
- 소모품의 실제 조회값 0이 마모 상태인지 모델 호환 문제인지 미확정입니다. 임의 초기화하지 않습니다.

## HACS·설치·보안

- 이전 0.7.1 서버와 실기로 확인한 원본 HACS는 **v2.0.2**입니다. v2.0.3의 인증서 SAN 검증 실패는 해결되지 않았습니다. v2.0.2의 연결 성공은 서버 인증서 검증 성공이 아닙니다.
- 기존 HA entry·엔티티·예약·지역·로봇 전용 네트워크 정책을 보존합니다.
- 현재 운영 환경의 DNS/TLS frontend/포트 배선은 이 작은 앱 수정과 별개입니다. 이 브랜치만 설치하면 모든 환경에서 바로 연결된다고 보장하지 않습니다.
- 기존 백엔드와 새 애드온을 같은 포트로 동시에 실행하면 안 됩니다. 이번 배포는 기존 애드온 하나를 업데이트했으며 두 백엔드를 병행하지 않습니다.
- 인터넷에 API/MQTT/Web UI를 공개하지 마세요. 원본의 인증 부재는 별도 한계입니다.
- 사용자 인증자료, 개인키, 장치 identity, 실제 지도/좌표를 커밋하지 않습니다. upstream에서 상속한 `app/certs/` 파일은 이 패치에서 열거나 수정하지 않습니다.
- upstream 0.9.1의 `upload_scheme: http`, HTTP 업로드 포트 19980을 사용합니다. 사용자가 승인한 **로봇→HA 내부망 지도·로그 업로드 경로**에 한정하며, API/MQTT의 TLS를 끄지 않습니다. 인터넷 포트 포워딩이나 공개 터널을 만들지 않습니다. HTTP는 전송 내용 암호화·서버 신원 검증을 제공하지 않으므로 신뢰하는 내부망에서만 사용합니다.
- upstream의 청소 전 지도 선택은 방/구역 청소에서 추가 로봇 명령을 보내는 변경이므로, 해당 기능은 별도 실기 승인 후 확인합니다.

## 개발 검증

Mac 등 개발 호스트에서 Python 3.12와 aiohttp를 준비한 뒤:

```sh
python -m unittest discover -s tests -v
```

또는 uv가 있으면:

```sh
uv run --no-project --python 3.12 --with aiohttp python -m unittest discover -s tests -v
```

시험 데이터는 합성 장치와 임시 디렉터리만 사용합니다. 운영 비밀 파일이나 로봇 연결은 필요하지 않습니다.
