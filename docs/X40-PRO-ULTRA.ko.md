# Dreame X40 Pro Ultra — 최소 호환 패치

이 브랜치는 [dwyschka/Dreame-local](https://github.com/dwyschka/Dreame-local)의 **0.9.1 / `df9160cee933626f08c112d9159f9a66cea38ccc`**에 필요한 수정만 적용합니다. 기존 별도 백엔드를 다시 넣지 않습니다. 이전 0.7.1 실기 결과를 0.9.1 검증 결과로 간주하지 않습니다.

- 대상 모델: **X40 Pro Ultra / `dreame.vacuum.r2401`**.
- 개발 브랜치: `x40-pro-ultra/compat`. 포크의 `main`은 upstream 그대로이며 이 패치가 없습니다.
- 기존 두 자체 제작 저장소는 아카이브했습니다. 코드를 삭제하거나 운영 애드온을 정지한 것은 아닙니다.
- 원본의 라이선스 표기를 변경하거나 별도 재배포 권한을 부여하지 않습니다. GitHub 포크 외의 바이너리/릴리스 배포는 하지 않습니다.

## 범위와 현재 검증 상태

### 속성 조회 결과를 HACS에 전달

로봇의 `/recv/` 속성 조회 응답은 서버 캐시를 갱신하지만, 원본 HACS는 `/status/`를 구독합니다. 원본은 이 응답을 status 이벤트로 전달하지 않습니다. 따라서 서버의 상태와 HACS 상태가 달라질 수 있는 경로가 있습니다.

최소 수정은 `device.py`의 기존 `_handle_recv`에서만 합니다.

- 실제 장치 응답 중 `code=0`이고 값이 있는 속성을 기존 `properties_changed` 형식으로 전달합니다.
- 서버 캐시와 같은 값이어도 전달합니다. 서버 캐시는 최신이지만 HACS가 오래된 경우를 포함합니다.
- 음수/실패 코드 또는 성공 여부가 없는 응답으로 캐시를 덮어쓰지 않습니다.
- 이 전달 자체는 추가 로봇 RPC나 청소/복귀 명령을 발생시키지 않습니다.
- 지도 service 6은 별도 프레임 변환 경로가 필요하므로 이 일반 속성 알림에 넣지 않습니다.
- 기존 명령 ACK 결과와 pending-future 상관관계는 유지합니다.

**회귀 시험:** 원본 함수로 전달 누락과 실패 응답의 캐시 오염을 재현한 뒤, 수정본에서 `tests/test_state_sync.py`의 시험이 통과했습니다. 합성 응답에 대한 검사이며 실제 로봇의 복귀 전환을 다시 시험했다는 뜻이 아닙니다.

**운영 검증:** 업데이트 전 직접 로봇 조회와 서버 상태는 충전 완료인데 HA 상태는 복귀 중인 불일치를 다시 확인했습니다. 사용자 승인 후 기존 애드온을 `0.9.1-x40.2`로 업데이트·재시작하자 HA Core 재시작 없이 HA 상태도 `charging_completed`, vacuum도 `docked`로 수렴했습니다. 이후 읽기 전용 장치 조회에서도 충전 완료와 오류 0을 확인했습니다. 기존 stale 증상 해소는 관측했지만 새 청소/복귀 전환을 시험하지 않았으므로 해당 상황의 장기 재발 방지를 확정하지 않습니다.

- native HAOS amd64 이미지에서 같은 회귀시험 **8개 통과**, 앱 소스 hash **8개 일치**를 확인했습니다.
- Mac→HA 내부망 HTTP 업로드 canary는 200 응답뿐 아니라 파일 내용 readback까지 확인하고 시험 파일을 제거했습니다. 실제 로봇이 새 HTTP URL로 올리는지와는 별도 검사입니다.
- 현재 지도 PNG는 실제 파일 생성과 전체 decode를 확인했습니다. 로봇 이동 없이 실시간 위치·궤적 갱신을 증명한 것은 아닙니다.
- 기존 options·포트·boot·watchdog·데이터 mount를 보존하고 HTTP 업로드 포트만 추가했습니다. HA Core·공유기는 재시작하지 않았고 새 물리 명령을 보내지 않았습니다.

### 한국어 웹 화면 (`0.9.1-x40.5`)

상태·제어 페이지와 지도·방 관리 페이지의 독일어 버튼, 상태 안내, 구역 이름, 확인창, 오류 안내를 한국어로 변경했습니다. 흡입 세기·물 사용량·청소 방식은 화면에만 한국어로 표시하며, 선택 항목의 명시적인 `value`, 명령 식별자와 API 값은 기존 그대로입니다. 지도에 저장된 사용자 지정 방 이름과 진단용 원본 JSON 키·코드는 바꾸지 않습니다. 흔히 쓰이는 로봇 상태도 표시용 한국어 이름으로 변환하되, 알 수 없는 값은 원문을 보존합니다. 번역은 청소 기능의 추가 실기 검증을 의미하지 않습니다.

운영 애드온 `0.9.1-x40.5`에서 두 페이지가 한국어 HTML을 제공하고 실행 중인 소스와 정확히 일치함을 확인했습니다. 실제 응답의 JavaScript를 네트워크 없는 합성 DOM/API 환경에서 실행해 상태 표시·선택값·명령 payload·취소한 확인창을 검사했고, 운영 이미지에서도 네트워크를 차단한 회귀시험 **24개**가 통과했습니다. 기존 방 6개와 지도 PNG(972×760)는 유지됐습니다. 이 검사는 사용자 휴대전화의 인증된 HA 화면을 직접 육안 확인한 것은 아닙니다.

### X40 상태·제어 보완 (`0.9.1-x40.6` 운영 적용)

- 사이드바 첫 진입을 `/` 상태·제어로 변경하고 지도·방 관리는 `rooms` 링크로 유지합니다. Supervisor가 생성하는 실제 경로와 두 라우트를 시험합니다.
- **흡입 청소 후 물걸레 청소**를 추가합니다. X40의 `CLEANING_MODE`는 단순 enum이 아니라 세척 설정을 포함한 묶음 값입니다. HACS v2.0.2의 모드 변환을 대조해 하위 모드 비트만 바꾸고 나머지 설정을 보존합니다. 작업 중 순차 청소 진입과 현재 설정을 모르는 경우에는 거절합니다.
- X40의 물 사용량은 `WATER_VOLUME`에 단순 enum을 쓰지 않고 `WETNESS_LEVEL`로 변환합니다. **수분 1~32단계**도 별도로 조절합니다. 수분 27 이상에서 세척 간격 변경이 필요할 수 있는 경우에는 웹이 다른 설정을 몰래 바꾸지 않고 HA에서 먼저 조정하도록 안내합니다.
- 기존 **충전대로 복귀** 버튼의 `return_to_base`를 실제 mapping의 `CHARGE` 액션에 연결합니다. 로봇이 반환한 실패 코드를 성공으로 표시하지 않고 화면에 오류를 표시합니다.
- 원시 HACS `set_properties` 경로는 재인코딩하지 않습니다. 새 제어는 합성 장치·가로챈 wire 명령으로 시험하며, 이 단계에서 실제 청소·복귀·세척 명령을 보내지 않았습니다.

- 작업 단계·스테이션 상태·청소/건조 진행률·물 경고·먼지 비우기 상태를 읽기 전용 카드로 표시합니다. 소모품 잔여율과 누적 면적/시간/횟수도 표시하되, 0을 누락시키거나 소모품을 자동 초기화하지 않습니다. 알 수 없는 코드는 정상으로 꾸미지 않습니다. 청소 시간의 잘못된 `초` 표시는 HACS의 `분` 단위로 수정했습니다. 원본 상태값은 HTML로 실행되지 않도록 이스케이프합니다.

- 방 청소에서 저소음 값 `0`을 강력 `2`로 바꾸던 기본값 처리, 정밀 수분과 다른 원시 물 사용량을 보내던 경로를 수정했습니다. 방/구역 청소는 같은 수분 해석을 공유하고 구역 payload에 반복 횟수·흡입·물 사용량을 포함합니다. 현재 설정이 없으면 임의의 세기로 시작하지 않습니다. 수분 27 이상에서도 면적별/지능형 세척은 불필요하게 막지 않으며, 시간별/방별 또는 주기를 모르는 경우에만 별도 세척값 변경을 요구합니다.
- 운영 기기의 HACS가 보고한 `self_wash_base`, `mop_pad_lifting`, `mopping_after_sweeping`, `wetness`, `wetness_level`, `self_clean_frequency`와 실제 수분 값 존재를 읽기 전용으로 대조했습니다. 이 호환 처리는 현재 `r2401`/펌웨어 `1642`를 대상으로 하며 다른 모델·펌웨어의 capability 전체를 보증하지 않습니다.

기존 애드온 업데이트·재시작으로 `0.9.1-x40.6`을 운영에 적용했습니다. 개발 호스트와 네트워크를 차단한 native HAOS 운영 이미지에서 회귀시험 **43개**가 각각 통과했습니다. 실제 제공된 두 페이지의 HTML이 실행 중인 템플릿과 같고, JavaScript 합성 DOM/API 시험도 통과했습니다. 운영 readback에서 첫 Ingress 경로 `/`, 상태 online/13/error0/task0, 해석된 현재 모드 `sweeping_and_mopping`, 수분 `23`, 방 6개, 지도 PNG 972×760 및 CRC/전체 압축 해제 성공을 확인했습니다. HA vacuum도 `docked`로 유지됐습니다. 앱 소스 hash 8개, 기존 options·포트·boot·watchdog 보존을 확인했고 HA Core·공유기는 재시작하지 않았습니다. 실제 로봇 동작 명령은 보내지 않았으므로 순차 청소·방/구역·스테이션의 실기 동작은 여전히 별도 검증 대상입니다.

JavaScript 시험은 `tests/check_web_scripts.js`이며 실제 HTML의 스크립트를 입력받아 0/누락/알 수 없는 값, HTML 이스케이프, 선택/버튼 payload, 명령 거절 표시, 취소 확인창을 검사합니다. 브라우저에서도 제공된 HTML과 합성 데이터·가로챈 fetch로 모드 표시와 순차 모드 선택 payload를 확인했습니다. 이는 실제 인증된 HA iframe이나 사용자 휴대전화 화면을 육안 검증했다는 뜻은 아닙니다.

**추가 누락으로 확인했지만 이번에 새 제어를 붙이지 않은 기능:** 물걸레 세척·건조 시작/정지, 기기 내 예약/시간대 조회·편집, DND/차일드락/카펫·AI·세척 세부 설정. HACS에는 조건부 구현이 있으나 웹에는 없으며, 특히 스테이션 동작은 복귀 이동까지 유발할 수 있어 별도 프로토콜 처리와 실기 승인이 필요합니다. 방/구역 청소와 지도 편집은 기존 `/rooms`에 있으므로 신규 누락으로 세지 않습니다.

### 지도와 그 밖의 한계

**404 수정 (`0.9.1-x40.4`):** 사용자 화면의 404를 받아 확인한 결과, `ingress_entry: /rooms`가 Supervisor의 기본 슬래시와 겹쳐 실제 경로가 `//rooms`였습니다. `ingress_entry: rooms`로 수정했습니다. 기존 `/rooms` 직접 요청 성공만으로는 잡을 수 없었던 결함이며, 생성된 경로를 실제 aiohttp 라우터로 요청하는 실패→성공 회귀시험을 추가했습니다. 재시작 직후 UID가 아직 비어 저장지도를 찾지 못하는 문제도 재현해, **DID가 정확히 같고 후보 계정 폴더가 하나뿐인 경우**에 한해 기존 지도를 읽도록 했습니다. 다른 장치·여러 계정 후보·이미 알려진 다른 UID로는 우회하지 않으며 identity/지도 파일을 수정하지 않습니다. 운영의 생성 경로 `/rooms`, 방 목록(6개), PNG(972×760)가 모두 정상이고 native HAOS에서 19개 시험이 통과했습니다. 인증된 HA iframe의 시각 확인은 여전히 사용자 화면 확인이 필요합니다.

**웹페이지 바로가기 (`0.9.1-x40.3`):** 관리자용 HA 사이드바 `드리미 X40`에서 기존 `/rooms` 페이지를 Ingress로 엽니다. 8099를 호스트에 새로 공개하지 않습니다. 실제 저장지도가 JSON `mapstr` 포장으로만 남은 환경에서 API는 지도를 읽지만 WebUI는 이를 거부해 지도 PNG가 404가 되는 문제를 재현했습니다. 기존 웹 decoder에 포장 해제만 추가했고, 유효한 raw frame·URL-safe 입력·손상 입력 처리도 회귀시험했습니다. 운영 적용 후 페이지·방 목록·PNG가 모두 200, 방 6개, PNG 972×760 전체 decode를 확인했습니다. 기존 상태 시험을 포함한 14개 시험이 native HAOS 이미지에서 통과했습니다. HA Core는 재시작하지 않았고 로봇 동작 명령도 보내지 않았습니다. 브라우저의 HA 로그인은 완료하지 못했으므로 인증된 iframe의 시각 렌더링까지 검증했다고 주장하지 않습니다.

- 원본의 저장 지도/PNG 표시는 확인됐지만 실시간 위치·궤적은 미검증입니다.
- 지도 프레임 수신/선택 경로를 별도로 조사합니다. 좌표·궤적을 임의로 만들지 않습니다.
- 청소/순찰 이력은 원본에서 미구현이며 이번 최소 수정 범위 밖입니다.
- 소모품의 실제 조회값 0이 마모 상태인지 모델 호환 문제인지 미확정입니다. 임의 초기화하지 않습니다.

## HACS·설치·보안

- 이전 0.7.1 서버와 실기로 확인한 원본 HACS는 **v2.0.2**입니다. v2.0.3의 인증서 SAN 검증 실패는 해결되지 않았습니다. v2.0.2의 연결 성공은 서버 인증서 검증 성공이 아닙니다.
- 기존 HA entry·엔티티·예약·지역·로봇 전용 네트워크 정책을 보존합니다.
- 현재 운영 환경의 DNS/TLS frontend/포트 배선은 이 작은 앱 수정과 별개입니다. 이 브랜치만 설치하면 모든 환경에서 바로 연결된다고 보장하지 않습니다.
- 기존 백엔드와 새 애드온을 같은 포트로 동시에 실행하면 안 됩니다. 이번 배포는 기존 애드온 하나를 업데이트했으며 두 백엔드를 병행하지 않습니다.
- 인터넷에 API/MQTT/Web UI를 공개하지 마세요. 원본의 인증 부재는 별도 한계입니다.
- 사용자 인증자료, 개인키, 장치 identity, 실제 지도/좌표를 커밋하지 않습니다. upstream에서 상속한 `app/certs/` 파일은 이 패치에서 열거나 수정하지 않습니다.
- upstream 0.9.1의 `upload_scheme: http`, HTTP 업로드 포트 19980을 사용합니다. 사용자가 승인한 **로봇→HA 내부망 지도·로그 업로드 경로**에 한정하며, API/MQTT의 TLS를 끄지 않습니다. 인터넷 포트 포워딩이나 공개 터널을 만들지 않습니다. HTTP는 전송 내용 암호화·서버 신원 검증을 제공하지 않으므로 신뢰하는 내부망에서만 사용합니다.
- upstream의 청소 전 지도 선택은 방/구역 청소에서 추가 로봇 명령을 보내는 변경이므로, 해당 기능은 별도 실기 승인 후 확인합니다.

## 개발 검증

Mac 등 개발 호스트에서 Python 3.12와 aiohttp를 준비한 뒤:

```sh
python -m unittest discover -s tests -v
```

또는 uv가 있으면:

```sh
uv run --no-project --python 3.12 --with aiohttp python -m unittest discover -s tests -v
```

시험 데이터는 합성 장치와 임시 디렉터리만 사용합니다. 운영 비밀 파일이나 로봇 연결은 필요하지 않습니다.
